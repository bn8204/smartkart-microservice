1. Executive Summary

SmartKart is a production-grade e-commerce platform designed following microservices architecture principles. The system demonstrates modern software engineering practices including:

  • Microservices Architecture - 5 independently deployable services
  • Cross-Platform Support - Single backend serving web (React) and mobile (Flutter) clients
  • Event-Driven Design - Choreography-based Saga pattern using RabbitMQ
  • Database per Service - 4 isolated PostgreSQL databases for data autonomy
  • API Gateway Pattern - Single entry point for all client requests
  • Production-Ready Features - JWT authentication, Swagger docs, Prometheus metrics, health checks

✅ Core Features Implemented

  • ✓ Login Screen - Secure JWT-based authentication with bcrypt password hashing (Web + Mobile)
  • ✓ Main Menu (Dashboard) - Product catalog with search, pagination, and category filters (Web + Mobile)
  • ✓ Detail Page - Product details with real-time stock information and cart integration (Web + Mobile)
  • ✓ Shopping Cart - Add/remove items with quantity management
  • ✓ Checkout Flow - Order placement with distributed transaction handling
  • ✓ Order Tracking - Real-time order status updates via Saga pattern
  • ✓ Admin Dashboard - Order management and product CRUD operations
  • ✓ Native Android App - Flutter mobile app with 13 screens, built APK files (Section 6.1)

2.2 System Design Elements

Architecture Decision Record

Chosen Architecture: Microservices with API Gateway

Rationale:

  • Scalability: Each service can scale independently based on load
  • Technology Diversity: Services can use different tech stacks if needed
  • Fault Isolation: Failure in one service doesn't bring down the entire system
  • Team Autonomy: Different teams can work on different services
  • Deployment Independence: Services can be deployed without affecting others
  • Database Autonomy: Each service owns its data, following bounded context

3.2 Layer Descriptions

Layer 1: Client Layer (Presentation)

Responsibility: User interface and interaction

Components:

React Web Application
  • Technology: React 18, React Router
  • State Management: Context API, hooks
  • Features: Product browsing, cart, checkout, order tracking
  • Communication: Axios HTTP client to API Gateway
Flutter Mobile App
  • Technology: Flutter 3.x, Dart
  • Architecture: Clean Architecture (presentation, domain, data layers)
  • State Management: Riverpod
  • Communication: Dio HTTP client to API Gateway
  • Storage: Flutter Secure Storage for JWT tokens

Principle: Both clients consume the same backend APIs, demonstrating true cross-platform capability.

Layer 2: API Gateway Layer (Entry Point)

Responsibility: Single entry point, authentication, routing, composition

Port: 8080

API Gateway Service
  • JWT Verification: Validates tokens for protected routes
  • Rate Limiting: Prevents API abuse (100 requests/15min per IP)
  • Request Routing: Proxies requests to appropriate microservices
  • CORS Handling: Manages cross-origin requests
  • API Composition: Aggregates data from multiple services (e.g., order details with user and product info)
  • Swagger Aggregation: Combines API docs from all services
  • Error Handling: Standardized error responses
  • Logging: Request correlation with X-Request-ID

Principle: Implements the API Gateway pattern, providing a unified interface to clients while allowing backend services to evolve independently.

Layer 3: Service Layer (Business Logic)

Responsibility: Domain-specific business logic, independent services

User Service (:3001)
  • Domain: User management, authentication
  • Endpoints:
    • POST /api/v1/auth/register
    • POST /api/v1/auth/login
    • GET /api/v1/auth/users/:id
  • Security: bcrypt password hashing, JWT generation
  • Database: sc_users (PostgreSQL :5432)
Product Service (:3002)
  • Domain: Product catalog management
  • Endpoints:
    • GET /api/v1/products (list, search, paginate)
    • GET /api/v1/products/:id
    • POST /api/v1/products (admin only)
    • PUT /api/v1/products/:id (admin only)
  • Features: Stock management, search, categories
  • Database: sc_products (PostgreSQL :5433)
Order Service (:3003)
  • Domain: Shopping cart, order management
  • Endpoints:
    • POST /api/v1/orders/cart/items (add to cart)
    • GET /api/v1/orders/cart/:userId
    • POST /api/v1/orders/checkout
    • GET /api/v1/orders/my/:userId
  • Saga Role: Publisher (order.placed events)
  • Event Consumer: Listens to payment.processed
  • Database: sc_orders (PostgreSQL :5434)
Payment Service (:3004)
  • Domain: Payment processing
  • Endpoints:
    • GET /api/v1/payments/order/:orderId
    • GET /api/v1/payments/:id
  • Saga Role: Consumer (order.placed events)
  • Event Publisher: Publishes payment.processed
  • Database: sc_payments (PostgreSQL :5435)

Principle: Each service follows bounded context from Domain-Driven Design. Services are loosely coupled and communicate via asynchronous events.

Layer 4: Data Layer (Persistence)

Responsibility: Data storage, persistence, querying

Pattern: Database per Service

PostgreSQL Databases (4 instances)
  • sc_users: User accounts, authentication
  • sc_products: Product catalog, stock
  • sc_orders: Carts, orders, order items
  • sc_payments: Payment transactions
Data Isolation Benefits
  • Each service owns its data schema
  • No cross-database foreign keys
  • Independent schema evolution
  • Service-specific optimization
  • Failure isolation

Principle: Follows the Database per Service pattern. Cross-service data access is done via APIs, not direct database queries.

Layer 5: Messaging Layer (Event Bus)

Responsibility: Asynchronous communication, event-driven workflows

Technology: RabbitMQ (AMQP protocol)

RabbitMQ Message Broker
  • Port: 5672 (AMQP), 15672 (Management UI)
  • Exchange Type: Topic exchange
  • Queues:
    • order.placed - New orders from Order Service
    • payment.processed - Payment results from Payment Service
  • Pattern: Choreography-based Saga
  • Durability: Messages persisted to disk
  • Dead Letter Queue (DLQ): Failed message handling

Saga Pattern Flow:

  1. User places order via Order Service
  2. Order Service creates order (status: PENDING)
  3. Order Service publishes order.placed event to RabbitMQ
  4. Payment Service consumes event
  5. Payment Service processes payment
  6. Payment Service publishes payment.processed event
  7. Order Service consumes event and updates order status (CONFIRMED/FAILED)

Principle: Implements eventual consistency and loose coupling between services. Allows for fault tolerance and retry mechanisms.

4. Entity Relationship (ER) Model

The SmartKart database design follows the Database per Service pattern from microservices architecture. Each service owns and manages its own database, ensuring loose coupling and independent scalability.

4.1 Database Overview

Database Service Tables Purpose
sc_users User Service users User accounts and authentication
sc_products Product Service products Product catalog and inventory
sc_orders Order Service carts, cart_items, orders, order_items Shopping carts and order management
sc_payments Payment Service payments Payment transactions and processing

⚠️ Important: No Cross-Database Foreign Keys

In microservices architecture, services do not share databases. References between entities in different databases are logical only - they are implemented through API calls, not database foreign key constraints. This ensures:

  • Database independence and autonomy
  • Ability to use different database technologies per service
  • Independent schema evolution
  • Service-specific optimization strategies

4.2 Entity Definitions

USER SERVICE - Database: sc_users

Table: USERS

Purpose: Store registered user accounts with secure authentication

PK id : SERIAL (Auto-increment primary key)
name : VARCHAR(255) NOT NULL
UNIQUE email : VARCHAR(255) NOT NULL (Login identifier)
password : VARCHAR(255) NOT NULL (bcrypt hashed, never plain text)
role : VARCHAR(50) NOT NULL DEFAULT 'customer' (Values: 'customer', 'admin')
created_at : TIMESTAMP DEFAULT CURRENT_TIMESTAMP

Indexes:

  • UNIQUE INDEX idx_users_email ON users(email) - Fast login queries

Constraints:

  • Email must be unique across all users
  • Password minimum 8 characters (enforced at application layer)
  • Role must be 'customer' or 'admin'

PRODUCT SERVICE - Database: sc_products

Table: PRODUCTS

Purpose: Master product catalog with inventory management

PK id : SERIAL (Auto-increment primary key)
name : VARCHAR(255) NOT NULL
description : TEXT
price : DECIMAL(10,2) NOT NULL (Precision for currency)
stock : INTEGER NOT NULL DEFAULT 0 (Available quantity)
category : VARCHAR(100)
image_url : VARCHAR(500)
created_at : TIMESTAMP DEFAULT CURRENT_TIMESTAMP
updated_at : TIMESTAMP DEFAULT CURRENT_TIMESTAMP

Indexes:

  • INDEX idx_products_name ON products(name) - Search queries
  • INDEX idx_products_category ON products(category) - Category filtering

Business Rules:

  • Price must be greater than 0
  • Stock cannot be negative
  • updated_at automatically updates on modification

ORDER SERVICE - Database: sc_orders

Table: CARTS

Purpose: Temporary shopping carts for users before checkout

PK id : SERIAL
FK(logical) user_id : INTEGER NOT NULL → users.id (User Service)
created_at : TIMESTAMP DEFAULT CURRENT_TIMESTAMP

Relationship: One user has one active cart (1:1)

Table: CART_ITEMS

Purpose: Line items within a shopping cart

PK id : SERIAL
FK cart_id : INTEGER NOT NULL → carts.id
FK(logical) product_id : INTEGER NOT NULL → products.id (Product Service)
quantity : INTEGER NOT NULL DEFAULT 1
unit_price : DECIMAL(10,2) NOT NULL (Snapshot from product)

Unique Constraint:

UNIQUE (cart_id, product_id) - Prevents duplicate products in cart

Relationship: One cart has many cart items (1:N)

Table: ORDERS

Purpose: Confirmed purchase orders (immutable after creation)

PK id : SERIAL
FK(logical) user_id : INTEGER NOT NULL → users.id (User Service)
total_amount : DECIMAL(10,2) NOT NULL
status : VARCHAR(50) NOT NULL DEFAULT 'PENDING'
shipping_address : TEXT NOT NULL
created_at : TIMESTAMP DEFAULT CURRENT_TIMESTAMP
updated_at : TIMESTAMP DEFAULT CURRENT_TIMESTAMP

Status Values:

  • PENDING - Order placed, awaiting payment
  • CONFIRMED - Payment successful
  • SHIPPED - Order dispatched
  • DELIVERED - Order completed
  • CANCELLED - Order cancelled
  • FAILED - Payment failed
Table: ORDER_ITEMS

Purpose: Immutable line items in an order (historical record)

PK id : SERIAL
FK order_id : INTEGER NOT NULL → orders.id
FK(logical) product_id : INTEGER NOT NULL → products.id (Product Service)
product_name : VARCHAR(255) NOT NULL (Denormalized for history)
quantity : INTEGER NOT NULL
unit_price : DECIMAL(10,2) NOT NULL (Snapshot at order time)

Design Rationale:

  • Denormalization: product_name and unit_price are copied to preserve historical accuracy
  • Immutability: Once created, order items are never updated or deleted
  • Audit Trail: Maintains accurate order history even if products are deleted or prices change

Relationship: One order has many order items (1:N)

PAYMENT SERVICE - Database: sc_payments

Table: PAYMENTS

Purpose: Payment transaction log for all orders

PK id : SERIAL
FK(logical) order_id : INTEGER NOT NULL → orders.id (Order Service)
FK(logical) user_id : INTEGER NOT NULL → users.id (User Service)
amount : DECIMAL(10,2) NOT NULL
status : VARCHAR(50) NOT NULL DEFAULT 'PENDING'
payment_method : VARCHAR(50) (e.g., 'CARD', 'UPI', 'NET_BANKING')
transaction_id : VARCHAR(255) (External gateway transaction ID)
created_at : TIMESTAMP DEFAULT CURRENT_TIMESTAMP

Status Values:

  • PENDING - Payment initiated
  • SUCCESS - Payment completed successfully
  • FAILED - Payment failed
  • REFUNDED - Payment refunded

Indexes:

  • INDEX idx_payments_order_id ON payments(order_id) - Query payments by order

CART_ITEMS Quantity must be >= 1 Application (validation layer)
ORDERS Total amount must match sum of order items Application (server-side calculation)
ORDERS Status transitions must follow valid flow Application (state machine)
ORDER_ITEMS Cannot be modified after creation Application (immutable pattern)
PAYMENTS Amount must match order total Application (Saga validation)

4.5 Cross-Service Data Access Pattern

🔄 How Services Access Data from Other Services

Problem: Order Service needs product details, but Product Service owns the products database.

Solution: Inter-service communication via HTTP APIs

// Order Service needs product price during checkout
// Step 1: Order Service makes HTTP request to Product Service
const productResponse = await axios.get(
  `http://product-service:3002/api/v1/products/${productId}`
);

// Step 2: Product Service returns product data
const { price, name, stock } = productResponse.data;

// Step 3: Order Service uses this data to create order
const orderItem = {
  product_id: productId,
  product_name: name,        // Denormalized for history
  unit_price: price,         // Snapshot at order time
  quantity: requestedQty
};

Benefits:

  • Each service maintains its own data
  • Services can change internal schema without affecting others
  • Clear API contracts between services
  • Enables polyglot persistence (different databases per service)

6.1.7 Sample Code - Login Screen Implementation

login_screen.dart (Excerpt)

import 'package:flutter/material.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';
import 'package:go_router/go_router.dart';
import 'package:smartkart_mobile/features/authentication/presentation/auth_controller.dart';

class LoginScreen extends ConsumerStatefulWidget {
  const LoginScreen({super.key});

  @override
  ConsumerState<LoginScreen> createState() => _LoginScreenState();
}

class _LoginScreenState extends ConsumerState<LoginScreen> {
  final _formKey = GlobalKey<FormState>();
  final _emailCtrl = TextEditingController();
  final _passCtrl = TextEditingController();

  @override
  Widget build(BuildContext context) {
    final auth = ref.watch(authControllerProvider);
    final controller = ref.read(authControllerProvider.notifier);

    return Scaffold(
      body: SafeArea(
        child: Center(
          child: SingleChildScrollView(
            padding: const EdgeInsets.all(24),
            child: Column(
              children: [
                Text('SmartKart',
                    style: Theme.of(context).textTheme.displaySmall),
                // Form fields...
                FilledButton(
                  onPressed: auth.isLoading ? null : () async {
                    if (!_formKey.currentState!.validate()) return;
                    await controller.login(
                        _emailCtrl.text.trim(), _passCtrl.text);
                  },
                  child: const Text('Login'),
                ),
              ],
            ),
          ),
        ),
      ),
    );
  }
}
